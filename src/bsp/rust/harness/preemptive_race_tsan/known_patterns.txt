# Lens 2 (Task 9) TSan classifier: KNOWN, pre-existing, BROAD debt patterns.
#
# One extended-regex PATTERN per line (matched with `grep -E`). Blank lines and `#` comments
# are ignored.
#
# MATCHING TIER — read this before adding a pattern: by DEFAULT a pattern is matched only
# against the finding's RACE SITE (the normalized one-line `SUMMARY: ThreadSanitizer:` text,
# same as TSan's own summary — see run.sh's `classify_block()`). Prefix a line with `DEEP `
# (e.g. `DEEP src/lib/printf\.c` below) to instead match it against EVERY frame of both racing
# accesses' full stacks (WARNING line through SUMMARY line). DEEP is a deliberate, rare
# opt-in, NOT the default: on the audio thread almost every finding's stack passes through the
# same call-graph-root ancestors (`AudioEngine::routine()`/`routine_task()`,
# `deluge_app_render`, ...), so a broad file/subsystem pattern marked DEEP would match nearly
# any audio-thread finding regardless of where the race actually is — silently absorbing a
# genuinely new race that merely happens to run on that thread (this exact bug shipped in
# commit 4a42871dd and was caught in review the same day; see the R4 Task 8 class-1/class-2
# notes below for the concrete evidence and the fix). Only mark a pattern DEEP when you have
# verified, via full backtrace, that its target frame is unambiguously the SAME finding in
# EVERY observed instance, AND that the target is a leaf/access frame for that finding (never
# a call-graph-root ancestor of unrelated work) — `src/lib/printf.c` below is the one
# currently-justified case.
#
# Order matters: run.sh checks `open_findings_patterns.txt` FIRST, so a line matching both
# (e.g. `loader.cpp:82` below, which is inside a file this list's broad `loader\.cpp`-style
# reasoning would otherwise also catch) is correctly bucketed as an open finding, not here.
#
# WHY PATTERNS, NOT EXACT LINES: an early version of this catalog used exact `SUMMARY:` line
# matches (Spike B's style). Running the harness fresh a few more times immediately produced
# a LONG tail of new exact lines — different song-load/UI/Arpeggiator/reverb fields lit up
# by run-to-run scheduling variance — all belonging to the SAME already-understood debt
# class: nearly the WHOLE app's main-thread/UI/song-model/reverb/playback-transport state was
# written assuming cooperative (non-preemptive) scheduling, and none of it was made
# thread-safe when the audio task moved onto its own real preemptive OS-thread/interrupt
# executor (a change that predates this task — see the embassy-scheduler-migration and
# audio-callback-relocation work). Exact-line matching against that class is an unwinnable,
# ever-growing whack-a-mole; a broad FILE/SUBSYSTEM pattern is the honest, maintainable
# classification — it says "yes, this is that same well-understood, out-of-scope debt",
# without pretending to have enumerated every specific field it can touch.
#
# What stays OUT of this file (by design, so it is never accidentally swallowed into "known,
# ignore"): anything on the actual storage/cluster/recorder/resource-manager data path this
# task exists to check — see open_findings_patterns.txt for that (checked first).

# TLSF allocator (crates/deluge_alloc/src/tlsf.rs): concurrent, unsynchronized malloc/free
# calls into the SAME shared TLSF heap from two threads (audio-thread voice allocation,
# recorder cluster-table growth, and other allocation sites) racing each other on the
# allocator's own internal free-list/block-header state. WIDENED to a file-wide pattern
# 2026-08-06 (this fix round): started as 8 pinned exact lines (R1, 2026-07-22), grew to 10
# (R4 Task 8, 2026-08-06, +80/+446), then a SINGLE additional fresh run in this fix round
# surfaced 6 MORE distinct exact lines (293, 295, 306, 309, 342, 96) not in that list --
# confirming (unlike loader.cpp/clip.cpp/song.cpp/playback_handler.h, which have stayed
# stable) this is NOT a file where line-pinning scales: the race is fundamentally "any two
# concurrent Tlsf::malloc/free calls", so which internal helper (search_suitable,
# remove_free_block, split, use_block, BlockHeader::size/set_prev_used, ...) happens to be
# executing at the exact moment of the race varies with allocation size and free-list state,
# not with anything a maintainer controls. Verified via full-stack backtrace on every new
# instance (all reached via deluge_alloc -> Tlsf::malloc -> use_block -> {remove_free_block,
# split} -> BlockHeader::{size,set_prev_used,...}, from EITHER GeneralMemoryAllocator::
# checkEverythingOk's heap walk or a live allocate/free call on a fast_allocator<T> pool) --
# same architectural gap, a different exact internal line each time. SITE-only (not DEEP) is
# still safe here: unlike AudioEngine::routine()/deluge_app_render, tlsf.rs's functions are
# leaf allocator internals, never a call-graph-root ancestor of unrelated work, so a new race
# whose OWN site lands in this file is, by construction, the same "allocator not
# thread-safe" gap, not a different bug hiding behind an ancestor. Includes the two generic
# core::ptr::read/write<*mut BlockHeader> monomorphizations the accessors lower to.
