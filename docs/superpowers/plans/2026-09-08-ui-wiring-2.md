# UI Wiring 2 — the action dispatcher Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give `MenuScene::take_action()`'s mailbox a consumer, so the five ported items that request
root-UI behaviour actually perform it, and so the ported settings items that can only write their own
layer can finally push back into legacy.

**Architecture:** F1 made the ported scene stack run inside the firmware as a guest UI
(`ShellHostUI`) behind a runtime toggle. The guest ticks the shell from `timerCallback`. This plan
adds one drain at the end of that tick: poll `MenuScene::take_action()`, switch on the
`MenuAction`, and perform the legacy call the enumerator names. Everything else here rides that one
seam — the performance-view mirror's sync calls, and two new enumerators that close the port→legacy
direction for the shortcut-version and screensaver settings.

**Tech Stack:** C++20, CppSpec (`sim/scenes_spec`, `tests/spec`), CMake + ninja, the level-2 shell
script harness and the level-3 application A/B built by F1 task 11.

**Spec:** `docs/superpowers/specs/2026-08-26-ui-migration-design.md` — §10.2 items 3, 5.1, 5.2 and 6.
`src/scenes/menu/action.h` is the contract this plan implements and is quoted throughout.

**Scope decision (Kate, 2026-09-08):** action dispatcher + the sync sites + §10.2 item 5.
`take_choice()` (§10.2 item 4) is **deferred to F3**: it needs `SampleBrowser::claimCurrentFile` and
legacy's `maybeGetParentMenu` re-rooting, which reach into legacy browser internals no port test can
reach, and it is the one piece whose correct behaviour is not specified anywhere.

## Global Constraints

1. **No new UI/UX.** Everything must be a port of something legacy already does. A comment saying
   "legacy has none" or "spec design, not a port" is a defect to **report**, not a decision already
   made. One flag is deliberately left standing — `src/shell/shell.cpp`'s `dim_grid`, marked
   OUTSTANDING by F1 task 12 because Kate deferred it. Do not remove it and do not treat it as
   decided.
2. **With the toggle OFF, nothing may change.** `shellMenuEnabled()` is
   `RuntimeFeatureSettingType::ShellMenu`, default Off. Every legacy file this plan touches must
   behave exactly as before when it is false. Verified mechanically at review: every `-` line must
   reappear as a stripped-identical `+` line, with any exception deliberate and named.
   **This plan has one structural exception and it must be argued, not assumed:** Task 5's sync
   calls run in `PerformanceView` unconditionally, toggle or no toggle. They are legal because they
   write only `src/scenes`' own mirror, which nothing reads with the toggle off — say so at each
   site.
3. `snake_case` / `PascalCase` / `k` constants under `src/scenes/` and `src/shell/`. The scenes
   library never includes `gui/` (except `gui/l10n/`) or `hid/` and never calls frame primitives.
   `src/shell/**` never includes `model/**`. No `Action::Kind::LockInput`.
4. Never edit `src/bsp/rza1` (retired dead source). Never commit `src/bsp/rust/Cargo.lock`.
5. Cite legacy by **symbol AND line**, and verify every line with numbered output (`grep -n`).
   Never count lines in output that does not carry them.

## Two planning findings that change the work

Both were found while writing this plan, by re-resolving the spec's own citations. **They are
requirements, not context.**

### Finding A — `take_choice()` is on `BrowserScene`, not `MenuScene`

`src/deluge/gui/ui/shell_menu_entry.cpp:62` says *"the ported one parks its choice in
`MenuScene::take_choice()`"*. It is `BrowserScene::take_choice()`
(`src/scenes/browser/browser_scene.h:381`, `browser_scene.cpp:416`). `MenuScene` has no such member.
`src/deluge/util/shell_menu_entry.h:80` has the same slip. Task 9 fixes both.

### Finding B — `action.h`'s five-site list is wrong in substance, and it is the list that calls itself the contract

`src/scenes/menu/action.h:124-147` lists five `PerformanceView` writes the dispatcher must mirror,
says the list is exhaustive, and says *"an implementation that covers four of them still ships a
stale mirror"*. It then warns *"nothing in this repository can check that list stays complete"*.

**Every line number in it has drifted, and one of the five sites is not what it says.** Re-resolved
by symbol against the current tree with `grep -n "defaultEditingMode *=\|editingParam *=" src/deluge/gui/views/performance_view.cpp`:

| `action.h` says | actually |
|---|---|
| 1. `releaseViewOnExit` `:1327-1332`, writes at `:1330-1331` | `releaseViewOnExit` opens at **`:1344`**; writes at **`:1347-1348`** |
| 2. `buttonAction`'s BACK arm `:788-791` | writes at **`:791-792`** |
| 3. `buttonAction`'s shift+KEYBOARD exit `:855-857` | writes at **`:873-874`** (`:855` is the `X_ENC` arm) |
| 4. `buttonAction`'s shift+KEYBOARD cycle `:865-868` | writes at **`:882`** and **`:884`** |
| 5. `focusRegained`'s `defaultEditingMode = false` `:189` | **there is no such write.** `focusRegained` opens at `:279` and writes neither bool. The `:190` write is in **`PerformanceView::PerformanceView()`**, the constructor |

So there are **four runtime sites, not five**, and §10.2 item 6's "four sync calls" was right where
`action.h`'s "five, and four is not enough" was wrong. The constructor write needs no sync call:
it runs once at static init and sets `defaultEditingMode = false`, which is the mirror's own default
(`g_perform_mode = PerformanceEditingMode::DISABLED`, `menu/nodes/actions.cpp:45`) — they already
agree. **Task 5 owns correcting this list**, and must re-verify exhaustiveness itself rather than
trusting either count.

  `menu_scene().take_action()` once and performs it. Later tasks add arms to its switch.
- Consumes: `MenuScene::take_action()` (`src/scenes/menu/menu_scene.h:611`), whose contract at
  `:595-610` is the reason this exists: a **one-slot mailbox with silent overwrite**, no `Action`
  announces a pending request, so *"poll after every tick, or requests are dropped or stale."*

- [ ] **Step 1: Read `take_action()`'s contract** (`menu_scene.h:595-611`) and
      `MenuActionRequest` (`src/scenes/menu/action.h:105-111`). Note `engaged()` and that reading
      clears the slot.

- [ ] **Step 2: Write the failing spec.** Model it on `tests/spec/gui/shell_host_ui_spec.cpp`'s
      existing fixture use. The load-bearing example is that the drain runs **on a tick where the
      guest rendered nothing** — that is exactly the case the mailbox's warning is about.

```cpp
it("drains the mailbox on every tick, not only on ticks that rendered", [] {
    fakelegacyui::reset();
    openGuestAtMenuRoot();                      // the harness helper task 1 adds
    menu_scene().request_action_for_test(MenuActionRequest{MenuAction::OpenSongMacros, 0});
    shellHostUI.timerCallback();                // no input, no render this tick
    expect(fakelegacyui::opened.size()).to_equal(1u);
    expect(menu_scene().take_action().engaged()).to_be_false();  // slot cleared
});
```

- [ ] **Step 3: Run it and watch it fail** with the dispatcher absent.
      `ctest --test-dir build/tests -C Debug -R shell_action_dispatch`.

- [ ] **Step 4: Implement the skeleton.** The switch has `None` and a `default:` that is
      unreachable-by-construction; the five verbs arrive in Tasks 2-4.

```cpp
void deluge::gui::ui::dispatchShellActions() {
	const scenes::menu::MenuActionRequest req = scenes::menu::menu_scene().take_action();
	if (!req.engaged()) {
		return;
	}
	switch (req.action) {
	case scenes::menu::MenuAction::None:
		break;
	// Tasks 2-4 add the five verbs here.
	}
}
```

- [ ] **Step 5: Call it from the tick.** In `ShellHostUI::timerCallback`, **after** `Shell::tick`
      and **before** the timer is re-armed. Cite why that order: the request is filed by
      `after_render()`, which runs inside `tick`, so draining before the tick would always be one
      tick late.

- [ ] **Step 6: Prove the ordering, not just the call.** Add an example that files a request from a
      node's `after_render` and asserts it is performed in the **same** tick. Then mutate: move the
      drain above `tick` and confirm that example — and only that one — reddens.

- [ ] **Step 7: Run every gate. Commit.**
