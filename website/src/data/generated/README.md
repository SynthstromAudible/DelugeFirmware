# Generated menu data

`menu-hierarchies.json` is the website's menu reference, written by
`website/scripts/generate-menu-hierarchies.mjs` (`pnpm run generate:menu-hierarchy`) from `menu-tree.json` below,
`website/src/data/menu-hierarchy-tags.json` (each row's version tag, by key or by `<section>/<key>`) and
`src/deluge/gui/l10n/english.json` (the clip settings context menu, which is not part of the menu tree).
`pnpm run check` fails when the file is not what those give, so a change that regenerates `menu-tree.json`
regenerates this file too. Each row is `{"key", "oled", "title", "code", "option"?, "tag"?, "children"}`: `key` is
the row's labels from its section's top level down, slugged (`midi-commands`), and names its anchor on the reference
page, `menu-<section>-<key>`; `oled` and `code` are the row's name, which a 7SEG display scrolls in full; `title` is the
title its page shows. A page a select press opens (`"select_chain"` below) is a row of the first item that opens it.
A node's values (the dump's `"options"`) are leaf rows marked `"option": true`. A page's drawn rows (the dump's
`"rows"`, and the mod matrix's selected-cable pages, which the generator names as main's reference does) are rows in
place of its select chain. The rest of this file is about
`menu-tree.json`.

## `menu-tree.json`

Generated by golden_vt_render's `menu_dump` scenario (`tests/integration/scenarios/menu_dump.cpp`) from the declarative menu
tree (`src/scenes/menu/nodes/`). Never edit this file by hand: `./dbt test --update ui-menu-dump`
regenerates it, and the `ui-menu-dump` gate fails when the menu tree no longer dumps to it.

Read `menu_dump_main.cpp`'s own file header for the full schema (it recovers and documents the
retired Python `DocEmitter`'s shape, then explains exactly how and why this dump's shape differs
from it). Three differences matter enough to repeat here, for anyone consuming this JSON rather
than just diffing it:

- **`"description"` is never present**, on any entry -- not even as `""`. `Node` (the type this
  tree is built from) carries no such data, so there was nothing to put there. Code written
  against the old schema's assumption that every entry has a `description` key will fail on this
  file's actual shape.
- **A `"multicontext"`-typed entry (a node with `dynamic_children` set) does not exist in this
  file today, and if one ever does, it means the dump tool has stopped and refused to run**
  rather than guess a JSON shape for it: `deluge_menu_dump` exits non-zero and prints the
  offending node to stderr instead of emitting anything. As of this writing no node in the tree
  uses `dynamic_children`, so this is a design gap flagged in code rather than something this file
  has ever actually contained. Do not assume a `"multicontext"` entry here means what the retired
  `doc_emitter.py`'s `"multicontext"` type meant -- that Python type had no `"children"` key at
  all; this dump has no verified equivalent yet. (E2 task 10 went looking for the first real
  `dynamic_children` node -- the MIDI device list and the CV/gate output selectors were the
  candidates -- and found that none of the three can be one: a submenu row is labelled from a
  static l10n string id, and a MIDI device's row label is a runtime string. All three ship as
  self-drawing custom items instead, so the count of `dynamic_children` nodes in the tree is still
  zero and is pinned by a spec.)
- **`"options"` lists the values a node offers**, in its list's order: a target row's name table (every choice it
  names; in a context the menu may leave some out), the node's static names, its names hook asked with an empty
  context once per output a selector picks and as the boot song's first clip's row editor sees it (so a gate output's
  CLOCK and RUN SIGNAL, a sound's USE SONG SETTINGS and a note row's NONE direction), or a toggle's two words, as its own page lists them. A node that offers none (a submenu, a number, a custom page) has no key. The file is not
  formatted by prettier (`website/.prettierignore`): `ui-menu-dump` compares it byte for byte.
- **`"rows"` lists the rows a page draws in its own list**, which no node stands for, each with its `"name"` and
  its `"options"` and `"rows"` where it has any. Only "DX7 parameters" has them (its eleven rows, the operators'
  seven, and the params each reaches). The reference lists a node's rows in place of the pages its select press opens.
- **`"select_chain"` is a second nesting key, beside `"children"`.** It appears on every node whose
  select press opens another menu instead of going up a level (legacy's
  `MenuItem::selectButtonPress`), and holds full nested entries in the same shape `"children"`
  does. A walker that recurses on `"children"` alone will miss **eleven** pages entirely: the four
  arpeggiator octave/note-mode variants, `cvSubmenu` / `gateModeMenu` / `gateOffTimeMenu`, and the
  four patch-cable pages (`source_selection` regular/range and `patch_cable_strength`
  regular/range) are named by no submenu literal anywhere, in the firmware or in this dump, and a
  `"select_chain"` entry is their only appearance. Nodes with no chain carry no key at all, as with
  `"available_when"`. The same node can appear under both keys (`unison_spread` and `voice_count`
  are ordinary children _and_ chain targets), carrying the same `"id"` in each -- deduplicate on
  `"id"` if you need a node set rather than a tree.
- **`"ref": true` marks a chain target that is already on the current path -- a cycle stub.** The
  patch-cable pages form a genuine two-hop loop (the cable-strength page's select press opens the
  range source picker, whose select press opens the strength page straight back), so nesting them
  in full has no finite spelling. A target that would repeat an entry already open above it on this
  path is emitted as a stub instead: `{"id", "name", "ref": true, "title", "type"}` -- the same
  `"id"` the full entry carries, no `"children"`, no `"select_chain"`. **A recursive walker must
  stop at `"ref"`**, or it will loop only if it also follows the id back; resolve the id against
  the full entry it has already seen on this path. `"ref"` appears on no other entry, so a consumer
  that ignores the key sees a normal childless node rather than a shape it cannot parse.
