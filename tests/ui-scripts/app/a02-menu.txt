# Level 3: **the acceptance test for the menu.** The ui-scripts gate (`tests/integration/checks/ui_scripts.py`) runs
# it on the fixture card, where every snapshot must match the golden. A card that still stores a menu setting this
# firmware does not have boots the same menu: `tests/integration/ui/scenes/stale_menu_setting_spec.cpp` pins that, and the
# settings channel's SC-UNKNOWN check pins that the stored entry survives a write.
#
# **The run does not mutate its input**, which matters because a test that edits its input is not reproducible. The
# fixture card holds no `SETTINGS/CommunityFeatures.XML`, so `RuntimeFeatureSettings::readSettingsInline` takes its
# `WriteDefaults` arm: its `mkdir` finds `SETTINGS/` already there and its `rename` of a root-level
# "CommunityFeatures.XML" that does not exist fails, so it returns having created nothing. Checked rather than
# reasoned: `git status --short tests/fixtures/` is empty after the run.
#
# **What this script presses, and why it presses exactly this.**
#
# Boot lands in `InstrumentClipView`, not the session view -- `boot.state` shows `led Clip on`
# and `led Synth on`, and a `SoundEditor::setup` breakpoint on the SELECT press below stops with
# `InstrumentClipMinder::buttonAction` one frame up (`model/clip/instrument_clip_minder.cpp`: its select-encoder arm
# gates on `currentUIMode == UI_MODE_NONE` and calls `openMenu`). That is **site 6** of the
# fourteen in `gui/ui/menu_entry.cpp`'s table, the site whose root is `soundEditorRootMenu` /
# `MenuContext::Root::Sound`.
#
# **Why a clip-carrying site.** `main`'s `SoundEditor::setup` assigns `newSound` only inside its
# `else if (clip)` arm, so a `setup()` with a null clip leaves `currentSound` null and dereferences
# null -- measured under gdb for site 1 (SHIFT+SELECT) and site 2 (SELECT from the session view) on the
# host sim; sites 3 and 4 pass the same null clip, by inspection. Latent rather than fatal on the
# device, where address 0 is mapped. The menu has no such crash, but this script stays on gestures
# `main` survives too, so its panels can be compared with `main`'s; the null-clip sites' roots are
# `menu_entry_spec`'s (`menu_entry_roots`).
#
# The shape: boot into a scene, one navigation, one edit gesture, one popup, back out.
#
# 50 ms rather than 0: the app blits its first frame from inside the main loop, after its first
# input poll, so nothing has been drawn at 0 ms (`a01-boot.txt`'s own note).

# **One MenuAction verb, performed end to end, from a real press.**
#
# Everything above is the *shape* of a menu visit. Everything below drives
# `MenuAction::SetClipLengthToSampleLength` through `gui::ui::dispatchShellActions`'s arm
# (`gui/ui/shell_action_dispatch.cpp`) and photographs the popup it raises, the popup `main`'s
# `audio_clip::SetClipLengthEqualToSampleLength::selectButtonPress` raises for the same verb.
#
# **Why this verb.** Of `MenuAction`'s five verbs, three sit in roots only the null-clip sites open
# (sites 1-4: Settings, Song, Performance), which `main` crashes on as noted above: `OpenSongMidiLearn`,
# `OpenSongMacros` and `OpenPerformanceView`. `StartStemExport` is
# reachable only from the song root (the same crash) or the kit-global-FX root, which needs a kit
# this empty card cannot create ("NO MORE PRESETS FOUND"), and would write stems to the fixture.
# That leaves this one.
#
# **The route is the gesture a user performs**, not a back door: convert the boot song's one (empty) synth clip to an
# audio clip in the song view -- hold its pad, press the select encoder (`SessionView::buttonAction` in
# `gui/views/session_view.cpp`, which calls `replaceInstrumentClipWithAudioClip`) -- enter it, open its menu (site 5,
# `AudioClipView::buttonAction` (`origin/main:src/deluge/gui/views/audio_clip_view.cpp`)), and walk ACTIONS -> SET CLIP LENGTH.
#
# **The timings below are not padding, and three of them are load-bearing.**
#
#   * **1700 -> 2900 before the first pad.** `SessionView::padAction`'s clip arm is gated on
#     `currentUIMode == UI_MODE_NONE` (`SessionView::padAction`), and the clip-view -> song-view
#     transition holds `UI_MODE_ANIMATION_FADE` (44, `gui/ui/ui.h`) for about a second. A pad
#     pressed inside that window is swallowed silently -- measured: `currentUIMode == 44` at a
#     `padAction` breakpoint 400 ms after the SESSION press.
#   * **pad 0 7, not pad 0 0.** `songViewYScroll` is -7 on a fresh song, so `getClipOnScreen(yDisplay)` is
#     `sessionClips[yDisplay - 7]`: row 7 is the song's one clip and row 0 is nothing. Pressing row 0 falls into the
#     *create* arm instead, and the SELECT that follows then reaches the no-clip `soundEditor.setup()` in
#     `SessionView::buttonAction` (`origin/main:src/deluge/gui/views/session_view.cpp`) -- site 2, i.e. the crash above.
#   * **6000 -> 6350, the whole tail.** `SET CLIP LENGTH EQUAL TO SAMPLE LENGTH` is wider than the panel, so the
#     selected row's label side-scrolls: the menu animates `ui::widgets::oled::scroll_text` inside `list` (`ui/widgets/oled/list.h`)
#     where `main` registers `OLED::setupSideScroller` (`Submenu::drawSubmenuItemsForOled` in
#     `origin/main:src/deluge/gui/menu_item/submenu.cpp`). **They stay in step for the first ~400 ms and drift apart
#     after it** -- measured at 50 ms granularity: byte-identical at 100/250/300/350/400 ms past the turn, different at
#     500 ms and beyond. So the press and its snapshot both happen inside that window. This is a real divergence and it
#     is recorded rather than dodged: it is the same `setupSideScroller`-has-no-port gap
#     `ui/scenes/menu/nodes/output_items.h` already lists, seen here on a menu row instead of an output name.
