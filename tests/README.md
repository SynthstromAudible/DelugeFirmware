# The test registry

`registry.toml` lists every test in the repository: the ctest suites under `tests/`, the cargo suites, the
component rigs (differentials, sanitizer stress runs, fuzzers) and the integration scenarios, each with its level,
runner, tier and prerequisites. `./dbt test` runs any selection of them:

    ./dbt test                          # the pr tier: what a pull request runs
    ./dbt test --level integration      # one level: unit, component or integration
    ./dbt test --tier nightly           # everything up to and including nightly
    ./dbt test <name> [<name> ...]      # by name, whatever the tier
    ./dbt test unit -- -R stitch_spec   # arguments after -- go to ctest
    ./dbt test --list                   # what exists, and what you can run right now
    ./dbt test --doctor                 # what is missing, and how to get it

A test whose prerequisites are missing is reported as skipped, with the reason; `--strict` (which CI passes) makes
a skip fail the run.

**The table below is generated.** Edit `registry.toml`, then regenerate:

    ./dbt test --list --markdown

## Where things live, and why

Placement follows coupling to the BSP source tree, not language or purpose.

- **`tests/component/differential/`** — harnesses whose subject is a `crates/` library or
  `cc`-compiled application C++, rather than the BSP itself.

  One of these, `fs_differential`, does reach into the BSP: its
  `tests/efatfs_core.rs` `#[path]`-includes `src/bsp/rust/src/efatfs_core.rs` so
  the host test drives the exact device module. That single reach does not move
  it, because the rule turns on what a package *is*, not on whether any line
  touches the BSP — its six-file library is BSP-free and its subject is the
  vendored `embedded-fatfs` stack in `crates/`. Contrast `lens1_vt_sim` and
  `golden_vt_render` below, which `#[path]`-include twenty-odd BSP files each:
  being a second compilation of the BSP is their whole identity.

  The cost of that exception is a four-level `#[path]` reach that breaks if the
  BSP tree moves, plus a `rustfmt.toml` in that package excluding the borrowed
  file from its formatting run (the two crates are on different editions and
  disagree about import order). Both are recorded here so the next person sees
  the exception rather than rediscovering it.
- **`tests/component/stress/`, `tests/component/dsp-diff/`** — standalone C++ rigs with their own `run.sh`, deliberately
  not ctest-driven.
- **`src/bsp/rust/harness/`** — harnesses that `#[path]`-include BSP source, so
  a change to a shared file is picked up by both the firmware and the harness.
  `lens1_vt_sim` and `golden_vt_render` are second *compilations* of BSP source,
  not copies of it; that is the whole point, and it is why they cannot move out.

Three constraints keep these as separate Cargo packages rather than one
workspace, and they are worth knowing before adding a tenth:

1. `[patch.crates-io]` is workspace-global. Only `src/bsp/rust/Cargo.toml`
   carries the embassy fork patch; a workspace spanning it and the host clock
   harnesses would force the fork onto them silently.
2. `embassy-time`'s `std` and `mock-driver` features both emit
   `#[no_mangle] _embassy_time_now`. Cargo unifies features across all targets
   of one package, so two time drivers cannot share a package — and
   `cargo build --workspace` cannot span them either.
3. Feature unification makes a shared workspace build a hazard even where the
   symbols do not collide.

## Build products and trees

A test declares the build products it needs in `builds`; `./dbt test` builds the union of a selection's products
once, dependencies first, before running any test (`scripts/tasks/test_builds.py`). No test builds a product
itself, so none can run against a stale one.

| Product | Tree | What it is |
| --- | --- | --- |
| `host-app` | `build/host-app` | the C++ app's object files for x86-64, from `sim/` with `DELUGE_SIM_X64=ON`; nothing links here |
| `golden-vt-render` | `build/cargo-harness` | the Embassy host harness binary every scenario gate runs; its `build.rs` archives `build/host-app`'s objects |

A ctest entry's own tree (`build/test-unit`, `build/test-unit-arm`) is configured and built by its runner.

Every cargo-built test and product shares `build/cargo-harness`. Cargo namespaces artifacts by fingerprint, so
packages with different `[patch]` sections coexist there safely, but cargo takes an exclusive lock per target
directory, so two runs at once serialize rather than run in parallel.

Running `cargo` by hand inside a harness directory bypasses this and creates a local `target/`, and one per
harness directory adds up to tens of gigabytes of duplicate build trees. Prefer `./dbt test <name>`;
`./dbt test --clean` drops every tree the runner builds.

## Adding a test

Add a `[[harness]]` block to `registry.toml` and regenerate the table. `gates` and `status` are mandatory: a test
that cannot state the regression it catches is one nobody can later decide to delete: a crate whose own header
declares it throwaway survives indefinitely when nothing records that fact anywhere a reader would look.

### A scenario gate

A scenario gate is a stepped scenario the Embassy host harness runs (`runner = "scenario"`). Adding one:

1. **The scenario:** `integration/scenarios/<name>_scenario.{h,cpp}`, exporting `begin`, `complete`,
   `dispatch_step`, `step_done` and `failures`, and a row in `integration/scenarios/scenario_table.cpp`. Only the host
   tree compiles that directory, so it needs no `DELUGE_HOST` guard, and includes are `"scenarios/<name>.h"`.
   golden_vt_render's one stepped driver runs any row by name; nothing on the Rust side changes, unless the scenario
   needs its own card (`main.rs`, the `match` on the scenario name).
2. **The registry entry:** `scenario = "<name>"`, `builds = ["golden-vt-render"]`, the `markers` each run must print
   and the `result` line that says it passed. `./dbt test` checks those, and the exit status, itself.
3. **A check, only if the gate needs more:** `tests/integration/checks/<name>.py`, named by the entry's `check`,
   defining `check(gate, run)` (after the standard run) or `run(gate)` (instead of it). See
   `scripts/tasks/scenario_gate.py`.
