# Golden-master audio regression harness

Bit-exact regression tests for the synth engine, and the safety net for the
synth untangling work ([docs/dev/synth_untangling_plan.md](../../docs/dev/synth_untangling_plan.md),
Phase 0). Every preset in `corpus/` is rendered offline through the host-sim
and the SHA-256 of the PCM must match the committed `fixtures.json`.

## How it works

Each case boots the **full application** in the host-sim with a generated FAT
card image containing one preset at `SYNTHS/PRESET.XML`. The blank-song boot
path (`Song::ensureAtLeastOneSessionClip`) loads the first preset from
`SYNTHS/` through the real deserialization path — no test-only loading code.
Each preset carries `inputMidiChannel="0"` so it is MIDI-learned to channel 1;
the harness then injects DIN MIDI events from the case's `.notes` script
(`default.notes` unless a case-specific one exists), keyed to the offline
audio clock so onsets are sample-exact. The host BSP renders deterministic
128-frame blocks to a WAV (`DELUGE_HOST_DETERMINISTIC` drives all clocks and
the dither seed off the rendered-frame count).

## Running

```sh
cmake -B build-sim -S sim -G Ninja && cmake --build build-sim --target deluge_host
python3 tests/golden/run.py                  # check against fixtures.json
python3 tests/golden/run.py --filter fm      # subset
python3 tests/golden/run.py --keep /tmp/wavs # save WAVs for listening
```

Requires `mtools` (mformat/mmd/mcopy) for the card images.

## The ARM-NEON oracle

The x86 build runs SIMDe portable code; the firmware runs hand-written
NEON/asm paths. Fixtures are only trustworthy if both agree, so cross-validate
against the arm-linux build (real NEON under qemu — the same `#if __arm__`
paths as firmware):

```sh
cmake -B build-sim-arm -S sim -G Ninja -DCMAKE_TOOLCHAIN_FILE=$PWD/sim/arm-linux-toolchain.cmake
cmake --build build-sim-arm --target deluge_host
python3 tests/golden/run.py --binary build-sim-arm/deluge_host \
    --wrapper 'qemu-arm -L /usr/arm-linux-gnueabihf -cpu cortex-a9'
```

Both architectures must pass against the *same* fixtures. This is mandatory
when re-baselining. (Isolated kernel diffs — `tests/dsp_diff` — are useful but
not sufficient: an out-of-bounds table read can return coincidentally-equal
garbage in a small test binary while diverging in the full app, which is
exactly how the FM gather bug behaved.)

## Re-baselining

A hash mismatch means the sound changed. If the change is intended:

```sh
python3 tests/golden/run.py --update
```

then justify the change in the commit message and re-run the ARM oracle.
Never baseline a silent render — the runner rejects peaks < 16 because
silence almost always means the preset failed to load (the fallback default
synth is not MIDI-learned).

## Extending the corpus

Cases are generated by `make_corpus.py` (edit it, re-run it, commit the
changed XMLs — the committed XMLs are the source of truth). Note scripts are
hand-written: `<frame> <hex MIDI bytes>` per line, `#` comments, frames in
nondecreasing order. Capture length defaults to 2 s; override per-case in
`SECONDS` in `run.py`.

Not yet covered (needs audio files on the card image): WAVETABLE and SAMPLE
sources, DX7 cartridges, sidechain from audio, mod FX / delay / reverb
(deliberately neutral in the corpus presets — they belong to a future
FX-chain corpus).
